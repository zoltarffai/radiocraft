# v0.2 architecture — Linux-only, Rust engine + web UI

Status: draft 2026-10-30. Supersedes docs/04 §GUI decisions (egui shell retired).

## Scope change vs v0.1

- **Platforms: Linux native only.** Drop Windows (mingw/Wine) and macOS (CI macos
  job) targets. CI keeps: tests + clippy + Linux AppImage job.
- **UI: replaced.** The egui shell (`radiocraft-app`, 3 740 lines) is retired.
  Its close-policy/reorder/search/selection/cue-plan *logic* tests move into
  `radiocraft-server` as regression tests; the egui rendering layer disappears.

## Language decision (locked)

**Rust stays — for the engine only.** The RE work proved RadioDJ's substance is
the real-time playout engine: gapless decode→cpal output, segue/crossfade math,
cart/zone mixing, `UpdateTracks2` one-transaction booking, BS.1770-4 loudness.
181 tests already validate this against the C# decompiles; rewriting it in
Node/Go/Electron would redo the one section where latency and correctness bite,
in the language least suited to it. **Web tech is used for the presentation tier
only.**

## Topology: one engine process, two shells, one UI codebase

```
┌────────────────────────────────────────────────────┐
│ radiocraft-server (binary)                         │
│  engine (audio/db/core/settings/net/plugin crates) │
│  + axum HTTP/WS on 127.0.0.1 (optional LAN bind)   │
│  + static asset host for the web UI                │
│  mode A: window  — Tauri WebKitGTK window + tray   │
│  mode B: browser — user opens http://127.0.0.1:port│
└────────────────────────────────────────────────────┘
┌────────────────────────────────────────────────────┐
│ radiocraft-window (thin Tauri shell)               │
│  webview → same URL; tray; close policy            │
└────────────────────────────────────────────────────┘
```

- Same UI code runs in any Chromium/Firefox and in WebKitGTK.
- Browser mode costs nothing extra (now-playing/webserver concept already
  exists in the net crate) and yields LAN phone-tablet operation later.
- Tray policy (MinimizeToTray parity) survives in the Tauri shell; browser mode
  runs headless.

## WS/HTTP contract (engine is the single source of truth)

- **State sync:** snapshot (JSON) + delta events. Event vocabulary mirrors the
  engine: `PlayerEvent {Started/Stopped/Finished/Paused…}`, per-zone
  now-playing `{SongData + cue plan + elapsed}`, playlists (main/queue/history),
  levels (peak/hold/rms per channel @ 20 Hz), clock/musics state.
- **Commands:** every GUI operation = one engine call (play/stop/cue/reorder/
  import/add-to-playlist/history ops/settings save). Commands are idempotent-
  keyed; engine refuses commands it can't honor (mirrors zone rules).
- **No business logic in JS**: validation/booking rules stay in Rust so both
  shells behave identically and stay covered by cargo tests.
- **Plugin ABI unaffected:** plugins call the host in-process, not via WS.

## UI stack (locked)

**Svelte 5 + Vite + TypeScript.** Rationale: web-components-lite small footprint,
no framework-specific wrapper needed in WebKitGTK, modern look is pure CSS.
Design target: dark radio-console look, keyboard-first transport ops.

## Crates plan (v0.2)

| crate | change |
|---|---|
| radiocraft-audio/db/core/settings/net/plugin | unchanged (all tests keep passing) |
| radiocraft-app | retired; logic tests migrated |

Note: `radiocraft-window` needs WebKitGTK/GTK3/appindicator devel packages. On machines
without them, build and test the rest with `--exclude radiocraft-window` (CI installs
the full dep set and builds every crate).

## Risks / mitigations

- WebKitGTK availability on target distros → it's a hard dep of the window mode
  only; browser mode always works; AppImage bundles nothing extra.
- Real-time metering over WS → 20 Hz push with last-value semantics; never block.
- Multi-client consistency → single engine, broadcast diffs; last-write-wins on
  commands is acceptable (RadioDJ was single-operator anyway).
